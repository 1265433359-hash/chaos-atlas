# 真实混沌工程师判定经验（Judgment Experience）

> 日期：2026-08-09
> 状态：项目负责人确认（"要把真实世界中混沌测试工程师的经验抽象进去"）
> 定位：知识库第三类资产——实验结果卡记录"这个系统哪里弱"，防御模式库记录"哪些机制能防住"，**判定经验记录"怎么判定一个症状是不是漏洞、值多少"**

## 一、为什么需要判定经验

我们当前的漏洞判定是**症状学**的：severity 3 = 超时/挂死/级联，2 = 延迟放大，1 = 无放大。这来自分类器/测量的客观规则，可复现、可审计。

但真实世界的混沌测试工程师不只看症状，他们判的是**"这个症状在业务上下文里意味着什么"**。同一症状（如 2s 延迟→4s 放大），在旁路组件和主路径上的含义完全不同。我们的 severity 没编码这层上下文，导致：

- OTEL-EMAIL（旁路 email 打挂主流程）和 OB-PAYMENT（主路径挂死）都是 severity 3，但真实工程师对前者评价更高——它暴露的是**架构耦合**，不只是缺超时
- TT-BASIC-500（500ms→520ms，1:1 无放大）按症状学是 severity 1 "弱"，但真实工程师会问"**有没有契约违约？**"——没有承诺就没有违约，它不是漏洞
- 恢复能力、可观测性、风险概率这些真实判定维度，我们的证据里有但没抽象成规则

判定经验 = 把真实混沌工程师的判定直觉**抽象成可复用、可迁移、有案例背书的规则**，供新项目接入时使用。

## 二、真实混沌工程师的五问框架

**① 它在业务主路径上吗？（影响面）**
- 旁路/非关键依赖同步阻塞关键路径 = **耦合缺陷**（架构级，价值最高）
- 主路径自身无保护 = 核心缺陷（常规严重）
- 独立旁路故障不影响主路径 = 低价值（可能连漏洞都不是）

**② 违约了吗？（契约）**
- 系统有无对外承诺（SLO / 超时预算 / gRPC deadline / 契约）？
- **违约才算漏洞**；没有承诺就没有违约
- gRPC 客户端 10s deadline → 挂到 10s = 违约 ✓；无契约的延迟放大 = 存疑

**③ 它恢复了吗？（恢复能力）**
- 注入停止后自愈，还是需要人工介入？
- **不自动恢复 = 严重度升级**（哪怕是中等症状）
- 探针重启"逃逸"注入、恢复超时是这类

**④ 我们能看见它吗？（可观测性）**
- 故障发生时能否被发现、定位、告警？
- 不可观测 / 无告警 = 运维黑洞 = 自身弱点（即使功能正常）
- OTel Jaeger 完整记录注入但无自动告警 → 部分弱点

**⑤ 它会真的发生吗？（风险 = 概率 × 影响）**
- 延迟/丢包/重启都是高概率现实事件（支付商超时、网络分区、滚动发布）
- 概率权重影响候选排序，不影响"是否漏洞"的判定

## 三、与现有 severity 的关系

判定经验不是替代 severity，而是**给 severity 加业务上下文**：

```
规则判定（症状）→ severity 1/2/3
经验判定（业务上下文）→ 修正/确认：
    severity 3 + 旁路耦合 = 升级为"架构级耦合缺陷"（高价值）
    severity 2 + 无契约违约 = 降级为"潜在风险，非漏洞"
    severity 1 + 不自动恢复 = 升级（恢复失败比症状本身严重）
```

修正必须有证据链：每条修正引用具体实验案例 + 反例，不靠主观。

## 五、首批条目（用本项目 17 个案例反推验证）

见 `tools/judgment_experience.py` 内 SEED 条目（每一条都引用本项目真实案例 + 反例）。核心条目预览：

1. **JE-COUPLING-001**：旁路组件同步阻塞主路径并挂到客户端超时 = 架构级耦合缺陷（severity 3+ 且升级价值）。证据：OTEL-EMAIL-LOSS-100、OB-CHECKOUT-EMAIL-FAILURE。反例：无（耦合即漏洞）。
2. **JE-CONTRACT-001**：gRPC 客户端有 deadline 且注入后挂到 deadline = 明确契约违约漏洞。证据：OB/OTEL/OB-CHECKOUT 全部 10s DEADLINE_EXCEEDED。反例：TT-BASIC-500（1:1 无违约）。
3. **JE-CONTRACT-002**：无契约承诺的延迟放大 ≠ 自动漏洞，需查是否有降级/兜底。证据：TT-STATION-DELAY-2000（4s 放大，HTTP 200 无违约声明）→ 判定为"潜在风险"而非"确定漏洞"。反例：有 SLO 的路径放大即违约。
4. **JE-RECOVERY-001**：注入停止后不自动恢复 = 严重度升级。证据：K7 探针重启恢复超时。反例：TT 系注入后恢复正常。
5. **JE-OBSERVABILITY-001**：故障被追踪系统完整记录但无自动告警 = 部分弱点（可诊断不可预警）。证据：OTel Jaeger 记录注入无 alert。
6. **JE-RISK-001**：高概率现实故障（支付商超时/网络分区）的弱点排序优先于低概率极端场景。
