# 方法论问题回顾（诚实审计）

> 日期：2026-08-09
> 目的：系统性审视"选择→注入→判定→知识"全链路，找出真实缺陷。分级：A=概念性缺陷（必须解决）、B=指标/统计不足、C=泛化与迁移缺口、D=闭环与一致性。

## A1. "防御住"与"没打穿"被混淆（最深的判定缺陷）

**证据**：`TT-STATION-DELAY-100`（100ms 注入→124ms 响应）判 severity 1 = "defended"；**同一个服务** `TT-STATION-DELAY-2000`（2000ms 注入→4017ms）判 severity 2 = "weakness"。同一服务，注入弱就"防御住"，注入强就打穿。

**问题**：我们把"**未观察到弱点**"当成了"**观察到防御**"。防御模式库里的 `weak_stressor` 条目（"注入强度低于触发阈值"）实际是**测量盲区**，不是防御模式——它混入了"防御能力"概念，污染了模式库。真实混沌工程师会做**注入强度扫描**（100ms→500ms→1000ms→2000ms）找防御边界，我们没有。

**修复**：判定必须区分三种状态——`打穿` / `防御住（有机制证据）` / `未达阈值（需扫描确认）`。severity 1 不自动进"defended"，除非有机制归因（如源码确认 timeout）。

## A2. 契约维度用错了参照物

**证据**：TT 系实验的 `request_timeout` 是 runner 参数（5s/8s），不是系统声明的契约。`JE-CONTRACT-002` 判"TT-STATION-DELAY-2000 无违约 → 潜在风险"——但这个"无违约"是在**我们自己设的 timeout** 上判的，不是系统承诺的。

**问题**：我们把"测量参数"当成了"系统契约"。真实混沌工程师判违约用的是系统的 SLO/gRPC deadline/配置声明的超时，不是测试工具的。

**修复**：契约采集必须独立于 runner——从源码/配置/服务定义里提取每个边的真实超时预算，runner 参数只做测量不定义契约。

## A3. 防御模式与判定经验都缺源码级验证

**证据**：`DP-DEFENSE-ABSORBED-001`（TT-BASIC-500 absorbed_by_design）基于观测推断"单调用路径无放大"，但**没有读 ts-basic-service 源码确认**是否有隐藏 retry/缓存。LLM 归因交叉验证的是"两个观测者一致"，不是"观测与实现一致"。

**问题**：模式库和经验条目是观测反推，缺源码/配置验证。真实混沌工程师会看代码确认机制，我们只看行为。

**修复**：模式条目加 `source_verified: bool` 字段；新条目默认 false，人工核对源码后置 true。

## B1. 对比结论无统计显著性

**证据**：M1 0.658 vs M0 随机 0.512-0.605 vs M3/M4 0.512——差异存在，但**没有置信区间、没有 bootstrap、没有显著性检验**。20 池只有 1 个池，replicate 3 次是 LLM 调用随机性，不是真实抽样。

**问题**：所有"谁更好"的表述都是点估计，审稿人会质疑。我们诚实声明了"统计功效有限"，但没做任何形式的重采样。

**修复**：对 severity 加权做 bootstrap（重采样 1000 次给 CI）；至少补 2-3 个不同的候选池（不是 replicate 而是真换池）。

## B2. severity 权重是拍脑袋的

**证据**：severity 3/2/1 权重是我们定义的。换成 5/2/1 或 3/2/0 排名可能变。**指标本身没有稳定性验证**。

**问题**：所有方法排名都建立在这组权重上，权重一变结论可能翻转。

**修复**：做权重敏感性分析（多组权重下排名是否稳定）；或在论文里把 severity 作为"分级呈现"而非"加权计分"。

## B3. LLM 判定无重测一致性

**证据**：M5 双轨 verdict 0.65、severity 命中 0.8——单次调用。deepseek-v4-flash 是随机采样（temperature=0.2），同一证据跑两次可能判不同结果。

**问题**：LLM 判定的方差未知，0.65/0.8 可能是运气好的那次。

**修复**：抽样验证——对 5-10 个候选跑 3 次，报告重测一致性（agreement rate）。

## C1. 故障家族单一，跨家族泛化是断言

**证据**：20 候选全是 NetworkChaos delay/loss + 2 个 PodChaos/StressChaos。**无组合故障、无 HTTPChaos（平台 blocked）、无 IOChaos/DNSChaos/TimeChaos**。

**问题**：方法在"延迟/丢包"家族验证充分，其他家族是断言不是实证。论文若声称"方法论适用于任意故障类型"会被挑战。

**修复**：至少补 1-2 个其他家族（组合故障、或解锁 HTTPChaos 后的单例）；论文限定"网络故障家族"或明示范围。

## C2. 降级迁移自动化未闭环

**证据**：`EDGE_TO_MECHANISM` 只有 2 条手搓边映射，覆盖 5/20 候选。"行为证据可推翻先验"实现了，但"**新项目自动匹配边指纹**"没有——迁移自动化停留在手写。

**问题**：跨项目降级的价值主张（省预算）依赖人工维护边映射，没有自动生成。

**修复**：从模式库自动生成边指纹索引（pattern.edge → candidate edge 匹配），新项目候选池接入时自动查询。

## C3. 探索→发现的验证成本没进模型

**证据**：M1 "5/5 命中"是**执行后**才知道的。真实新项目里 M1 选完还需人工注入验证，这个验证成本（时间/预算）没进对比——M1 的 0.658 有"我们替它完成验证"的后验增益。

**问题**：我们声明了但没量化。审稿人会问"M1 的探索成本 vs M4 的排序成本公平吗？"

**修复**：对比里加"每发现一个弱点所需的注入次数"成本指标（M1 探索 5 个 = 15 次注入验证 vs M4 排序 0 额外成本）。

## D1. "外部方法"不独立

**证据**：M1 声称是"外部方法"（ChaosEater），但它的候选池是我们建的、执行验证是我们做的、adapter 是我们提取的。**"外部方法的独立复现"实际上依赖我们全部基础设施**。

**问题**：论文若称"M1 是独立外部基线"会被审稿人反驳——它离"独立复现"很远。

**修复**：表述改为"ChaosEater 选择逻辑的 adapter 化重实现"（我们已部分这样声明），明示其依赖我们的池/验证链。

## D2. 知识资产语言/一致性

**证据**：知识卡片英文、判定经验中文、模式库英文。跨项目检索 `query_knowledge_base.py` 按 token 匹配会漏。

**修复**：统一检索层做双语归一化，或判定经验条目补英文 rule。

## D3. 环境漂移未记录

**证据**：train-ticket-lab 曾消失重建，secret 随机生成；Chaos Mesh 版本/内核状态（HTTPChaos blocked）影响实验。

**问题**：跨批次结论（早期 TT 实验 vs 现在）环境不完全一致，未记录每次实验的集群/内核/版本指纹。

**修复**：runner 报告里加 `environment_fingerprint`（集群、Chaos Mesh 版本、内核）。

## D4. 外部反馈闭环未完成

**证据**：我们证明了"能发现弱点"（M1 5/5、20/20 全执行），但**没提交 issue 给上游验证"我们发现的弱点被维护者认可"**——只起草了 train-ticket 的 issue。

**问题**：愿景里"向项目负责人报告漏洞证明可行性"这条还没闭环。"我们发现的弱点在真实项目里有价值"没有被外部确认。

**修复**：提交 train-ticket issue + OTel quoteShipping issue（原计划支线 1），把回复写进论文"工业影响"。

---

## 总结：最该先解决的三个

1. **A1（防御住 vs 没打穿）**——污染判定体系和模式库，必须修
2. **B1（无显著性）**——所有"谁更好"没有统计背书，审稿人必挑
3. **D4（外部反馈）**——愿景闭环的最后一步，成本最低收益最大
