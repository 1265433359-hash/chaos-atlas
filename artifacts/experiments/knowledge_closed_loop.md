# 知识库完整闭环方案（Learning Loop Architecture）

> 日期：2026-08-09
> 定位：把"不断学习迭代的知识库"从定位变成可运行的机制——四层循环、组件职责、证据回流、反例修正、审计与防漂移。
> 与既有资产的关系：知识卡片（薄弱点）、防御模式库、判定经验、选择经验是**记忆**；本方案是让记忆**学习、修正、遗忘**的神经系统。

## 一、核心隐喻

```
LLM = 假设生成器（提出"可能测哪 / 可能是什么弱点"）
证据链 = 验证器（受控注入 + 三态判定 + 契约清单，把假设变成事实）
知识库 = 记忆（四类资产，可检索）
审计 = 免疫系统（反例检测、置信度、变更日志，防止记忆腐烂）
外部反馈 = 世界裁判（上游维护者确认/拒绝我们的发现）
```

## 二、四层循环（从内到外）

### 循环 1：实验级闭环（单项目内，已部分实现）
```
实验（runner + gate）→ 证据 JSON → 摄入 → 三态判定 → 更新知识 → 指导下一轮候选
```
- 已实现：gate、三态判定、证据骨架、知识卡
- 缺：证据→知识条目的**自动回流**（现在靠手工）

### 循环 2：方法论级闭环（跨项目迁移）
```
新项目 → 检索选择经验（选哪测）→ 检索防御模式（哪不测/降级）→ 注入 → 新证据 → 回流修正旧规则
```
- 已实现：选择经验、降级查询（半自动）
- 缺：新项目证据回流后**自动更新**"13/14 是网络故障"这类统计性规则

### 循环 3：外部反馈闭环（真实世界裁判）
```
发现弱点 → 提交 issue → 维护者确认/拒绝/无回复 → 校准"我们的判定是否正确"
```
- 已实现：两份 issue 草稿
- 缺：提交 + 状态追踪 + 结果回流到知识库（确认 → 置信度升；拒绝 → 标记复核）

### 循环 4：LLM 增强闭环（知识 ↔ LLM 互相强化）
```
知识检索 → 喂 LLM 决策（选择/判定）→ LLM 输出=假设 → 验证 → 新知识 → 下次 LLM 决策更好
```
- 已实现：M5（证据→判定提升 15pp）
- 缺：**验证后的结果自动写回知识库**，形成"知识→LLM→验证→知识"的增益回路

## 三、组件清单与职责

| 组件 | 职责 | 现有状态 |
|---|---|---|
| **evidence_ingest** | 摄入 runner JSON/classification，标准化为证据记录 | ⚠️ 散在各工具 |
| **truth_engine** | 三态判定 + severity + 契约对照（verdict_for + contract_inventory） | ✅ |
| **knowledge_updater** | 证据 → 四类资产的增/改/删（含反例检测） | ❌ 需新建 |
| **counterexample_detector** | 新证据与旧规则冲突 → 标记"待裁决"而非静默改 | ❌ 需新建 |
| **confidence_state** | 每条知识：confidence + evidence_count + source_verified 三字段状态机 | ⚠️ 部分有 |
| **audit_log** | 每次变更：时间、证据来源、改动类型（增强/修正/删除）、触发者 | ❌ 需新建 |
| **query** | 决策时读取最新知识（已支持 cards/judgment/selection/patterns） | ✅ |
| **decision_engine** | 组合选择经验排序 + 防御降级 + 判定经验 → 候选优先级 | ⚠️ 半自动 |
| **issue_tracker** | issue 提交/状态/外部结果回流 | ❌ 需新建（草稿已备） |

## 四、证据回流规则（正向与负向）

### 正向（增强）：新证据支持旧规则
- 该条目的 `evidence_cases` 增加新案例
- `evidence_count += 1`，confidence 按阈值升级（如 ≥3 案例 → high）
- 示例：SE-NETWORK-FAMILY 的"13/14"→ 新项目确认弱点后 → "16/19"

### 负向（修正/遗忘）：新证据与旧规则冲突
- `counterexample_detector` 命中 → 条目标记 `contested`，不静默改
- 裁决（人工或 LLM+人工确认）：
  - 反例合理 → 规则修正（补反例边界）或置信度降级
  - 反例是噪音 → 记录并忽略
- 删除有严格条件：仅当 `source_verified=false` 且被 ≥2 个独立反例证伪（A1 删 weak_stressor 即此类）
- **修正/删除必须进 audit_log，绝不无声**

### 证据强度分级（裁决依据）
```
源码事实（WithTimeout 在 main.go）> 受控实验结果（r1-r3 复现）> LLM 归因（需验证）> 语料统计（频次）
```
冲突时低强度证据让位于高强度证据。

## 五、防漂移机制（防止知识库腐烂）

1. **每条知识 = {rule, evidence_cases[], counter_examples[], evidence_count, confidence, source_verified, last_updated, provenance}**
2. **置信度状态机**：draft → validated(≥1 案例) → corroborated(≥3 案例) → contested(反例) → deprecated
3. **反例是必填字段**：没有反例边界的规则不允许进库（已部分落实：判定/选择经验都有 counter_example）
4. **变更可追溯**：audit_log 记录"这条规则为什么变成现在这样"，新项目引用时能看到演变
5. **过期检测**：N 轮实验未被引用/未被证据触达的规则 → 标记 stale 待复核

## 六、闭环衡量指标（学习效果可量化）

| 指标 | 含义 | 数据源 |
|---|---|---|
| 知识新鲜度 | 每条知识多久未更新 | audit_log |
| **命中率演进** | 用知识选候选 vs 不用知识的命中差异（M1 5/5 是基线） | 前瞻对比 |
| 降级节省 | 模式库覆盖/降级的候选数 ÷ 总候选 | decision_engine |
| 判定准确率演进 | M5 判定准确率随知识库增长的曲线 | 每轮 M5 重测 |
| 外部确认率 | issue 被维护者接受 ÷ 提交数 | issue_tracker |
| 修正率 | 被反例修正/删除的规则 ÷ 总规则 | audit_log（证明系统在真学习） |

## 七、落地路径（按成本排序）

1. **P0（快，1-2 天）**：`knowledge_updater` 最小版——新实验证据自动追加到对应条目 evidence_cases + 更新 evidence_count/confidence；`audit_log` 记录每次变更。接现有 `assess_selection_evidence`。
2. **P1（中）**：`counterexample_detector` + `contested` 状态 + 裁决接口（人工确认）。接 A1 式的修正流程。
3. **P2（慢）**：`decision_engine` 完整版——选择经验 + 降级 + 判定经验组合成"新项目接入时自动出候选优先级 + 跳过建议"。
4. **P3（外部）**：`issue_tracker`——两份 issue 提交、状态追踪、维护者回复回流（确认→置信度升）。
5. **P4（闭环验证）**：跑一轮"知识库增强的 LLM 选择 vs 盲选"（用更新后的知识喂 M1 再测）——量化"学习有没有让方法变好"。

## 八、与既有计划的关系

- 导师汇报第十章"LLM 决策基准实验"= 循环 4 的最小版（知识→LLM→判定）
- 本方案把它规模化：从"一次实验证明知识有用"到"知识库随每次实验自动进化并反哺 LLM 与决策"
- 论文卖点升级："不是一次性方法论，是可自我修正、可量化学习效果的知识闭环"

## 九、必须诚实的两点

1. **闭环的价值要能度量**：P4 若不跑，"学习迭代"仍只是设计。衡量指标（命中率演进等）必须在实现后真的测。
2. **自动回流 ≠ 自动可信**：LLM 归因回填的模式（backfill）只能进 `validated` 之前的 `draft` 状态，源码核对后才 `source_verified`——防"垃圾进垃圾出"。
